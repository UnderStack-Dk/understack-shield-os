# Contributing to UnderStack Shield OS

Thank you for helping shape the project before implementation begins.

## Before opening work

1. Search open issues and discussions to avoid duplicate proposals.
2. For material architecture, privacy, or security changes, open an issue first.
3. Record accepted consequential decisions as an ADR.
4. Do not add product code, build pipelines, tracking, or implementation-specific dependencies without an approved proposal.

## Branches and pull requests

Create branches from `develop` (or `main` while `develop` has not been established) using `docs/`, `proposal/`, `security/`, `privacy/`, `chore/`, or `adr/` prefixes. Keep each pull request narrowly scoped, complete the template, and link its issue when applicable.

Pull requests need the required reviews and checks configured in GitHub before merge. The owner retains final approval authority for `main`.

## Writing standard

State assumptions, alternatives, trade-offs, and open questions. Use precise, non-marketing language. Privacy and security claims must be bounded and evidence-oriented: do not promise absolute security or anonymity.

## Coordinated disclosure

Security-sensitive material belongs in the private reporting process in [SECURITY.md](SECURITY.md), not in public issues or pull requests.
